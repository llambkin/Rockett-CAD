## Purpose

Build self-hosted browser-based parametric CAD for designing and manufacturing
parts. B-Rep solids, editable sketches, stable references and feature-history
regeneration are the foundation. Assemblies, CNC/CAM with pluggable posts,
a KiCad bridge, electrical tools and additive export extend that foundation.
Third-party plugin loading follows a proven first-party API.

Users sign in. Their settings and workspace preferences live on the server
and follow them across browsers. Target one user initially and up to three
collaborators, with conflict-safe editing rather than real-time co-editing.
Run privately in Docker with separate development and production data.
Large-model support is demonstrated against declared fixtures and budgets.

## Rulings

Carried forward from Mark's rulings dated 2026-09-23:

- Support first-party and third-party plugins.
- Bridge to KiCad rather than build a native PCB editor.
- Support pluggable CNC post-processors; qualify individual controller dialects.
- Core licence: set by DEC-001 from the upstream author's grant; the upstream
  repository has no licence today. Respect each plugin author's terms and attribution.
- Store per-user profiles and settings on the server.
- Use local-volume storage first; share mounts, WebDAV and Nextcloud are later options.
- No artificial project limits. Keep resource budgets explicit and failures recoverable.
- Deploy privately. Keep real deployment settings and operational evidence outside this repo.
- This public repository contains application code and project documentation only.
- Reuse suitable code and support substantial UI customisation.
- Safe, verified commits may be pushed to origin/main, subject to the cost,
  publication and production approval boundaries in AGENTS.md.

## Delivery and acceptance

REL-001 proves the core modelling product. REL-002 proves personal workspaces,
conflict handling and recovery. REL-003 proves the cross-workbench manufacturing
workflow, including the separately approved machine qualification. REL-004
checks release readiness. Implementation phase checkpoints do not replace these.

The phase index is: OPS hygiene; BUG defects; KIT shared primitives; DOC storage;
REF references; REL-001 core gate; AUTH identity; SET settings; UNDO history;
REG registries; CUST customisation; PERF scale; EXCH interchange; ASM assemblies;
PLUG modules; CAM machining; PCB bridge; ELEC electrical; PRINT additive;
REL release gates.

Rows below are in dependency order, rather than forcing all rows of one phase
to finish before a prerequisite from another phase. IDs retain their original
phase ownership. `scripts/check-work-order.sh --next` names the next row: the
first ready row in file order. Take that row; file order is the priority.
Rows parked by a decision, operator step, deferral or Proposed entry are skipped,
so independent work continues while they wait.

## Constraints

- Follow AGENTS.md, the coding standard and the complexity skill. Inspect the
  current implementation before choosing a design or applying a historical line reference.
- Original versions, counts, timings and source line numbers are baseline notes,
  not verified-current facts. Verify exact packages, licences, controller behaviour
  and file-format claims against pinned inputs and primary evidence when that row runs.
  Never encode a desired audit answer as an observed result.
- New tests use the existing workspace test folders; module tests use
  modules/<id>/test. OPS owns explicit discovery and DOM/browser separation.
- Every schema or naming change has old-format fixtures, a complete recoverable
  backup and a tested restore path. No automatic live-data migration is authorised here.
- Persist one owner per fact. Reuse KIT/REG/SET owners already introduced; later
  rows target their current locations, not deleted historical copies.
- Unknown module JSON survives semantically unchanged; source blobs remain byte-identical.
- Bound input bytes, nesting, decompression, jobs, retries, history and caches.
  A resource protection limit is not an artificial commercial project cap.
- Numeric CAD correctness, actual browser interaction and independent file
  interoperability are separate evidence. A DOM mock or self-generated golden
  cannot substitute for all three.
- Performance checks state fixture, anonymous hardware class, runtime, repetitions,
  warm-up and median/p95 budgets before judging a result. Keep machine details private.
- Visual changes use an approved design. Rows composing existing patterns follow DEC-004; a
  new screen layout, region, gesture, overlay kind or palette needs its own approval. Prepare designs before requesting approval.
- No paid action, public transmission, credential operation, production change or
  machine motion is authorised by a todo row. Apply the existing exact approval rules.
- Out of scope: native PCB routing, hosted cloud service, public deployment,
  mobile layouts and real-time multi-cursor editing. Do not add these indirectly.

## Agent loop

1. Read AGENTS.md, this header, the selected row and LAST-RUN.md. Confirm the
   active work order is adopted. Preserve unrelated work; inspect origin/HEAD
   and fast-forward only when safe without stashing or overwriting another task.
2. Run scripts/check-work-order.sh and take the row --next prints.
   `scripts/check-work-order.sh --row <ID>` prints one row from whichever file holds it.
3. Claim only that row as in-flight. Check its decision outcomes, scope and
   dependencies. A decision choosing an alternative requires its dependent rows
   to be reconciled before execution; merely marking the decision done is insufficient.
4. Inspect named code. Write the rejecting proof and watch it fail for the
   intended reason, then implement and pass it. Documentation-only work uses
   a document/queue contract check; do not damage working code just to create red.
5. Run the focused proof, then npm run check and git diff --check.
   Run browser, benchmark, compatibility and restore checks where required.
   Read the full diff. A passing test command must discover the intended tests.
6. Mark done only with evidence of the complete Outcome. Write the short handoff
   and any README feature line the row changes in the same verified change, then commit only intended paths and publish only
   after the required public-source and indirect-cost checks. Never push unrelated commits.
7. Scope changes go under Proposed for Mark. A blocked row does not authorise
   weaker tests, arbitrary new scope or repeated speculative fixes. Continue only
   independent authorised work and report the dependency that blocks progress.

## Rows

Columns: ID, Outcome, Status, Depends, Scope, Check. No pipe inside a cell.
IDs are stable and never reused. Dependencies appear earlier in this file.
Status is todo, in-flight, done, decision, operator or deferred. A deferred row
needs a Rulings line `- Deferred <ID>: <reason>` and never satisfies a
dependency; its dependants wait.
A list item under Proposed that starts with row IDs and a colon, such as
`- A-001, A-002: reason`, parks those rows and their dependants until the entry
is resolved and removed. IDs after the colon are only references.

Done and in-flight require every dependency done. Operator means unfinished
human work, not a completion exemption. --complete rejects every unfinished
required row, including decisions and operator actions. A checkpoint depends on
every row of its phase except those listed in one `Explicitly excluded: A, B.`
sentence. Excluded rows remain outstanding and cannot be claimed as delivered.

Done rows move to `docs/internals/work-order-done.md`, one line each with the
commit that landed them, and still count as done. The checker reads
`docs/internals/work-order-later.md` in place of the `Later phases:` line, so
file order and dependencies hold across all three files.

Every row may also update its own status, the handoff, directly affected tests,
and the existing document owning a changed contract. Source paths in Scope
are current ownership boundaries, not permission to ignore necessary proof.
If a refactor has moved an owner, update the row path before work. Split an
oversized row without losing its original outcome or acceptance gate.
